# Перенесення n8n з хмари на власний сервер

Підготовлено 13.08.2026. Тут лежить усе потрібне для переходу. **Нічого з цього
ще не запущено** — установка робиться тільки після рішення власниці.

| Файл | Що це |
|---|---|
| `docker-compose.yml` | опис контейнера n8n: порт, ліміти, змінні |
| `install.sh` | установка з перевіркою ресурсів; Caddyfile не чіпає |
| `update.sh` | оновлення з копією і **автоматичним відкатом**, якщо не піднялось |
| цей файл | план переходу і що потрібно від власниці |

---

## 1. Чому це взагалі варто робити

- воркфлоу й доступи опиняються **у вашому контурі** і потрапляють у щоденні копії;
- зникає залежність від акаунта й тарифу n8n Cloud;
- дані клієнтів не ходять через чужу хмару.

Проти:

- обслуговування (оновлення, простої, безпека) стає вашим;
- n8n Cloud тримає доступність краще, ніж це робитимемо ми;
- усе опиняється на одному сервері.

## 2. 🔴 Головне обмеження — ресурси

Перевірено на сервері 13.08.2026:

| | |
|---|---|
| Пам'ять | **2 ГБ усього**, вільно ~765 МБ |
| Процесор | **1 ядро** |
| Диск | 16 ГБ вільно — запас є |
| Swap | **немає** |
| NocoDB займає | 620 МБ |

n8n у спокої — 300–500 МБ. Небезпека не в тому, що впаде n8n, а в тому, що
при сплеску система вб'є **NocoDB, тобто ЕРП**.

Два допустимі варіанти:

**А. Збільшити дроплет до 2 CPU / 4 ГБ** (≈ $12 → $24 на місяць).
Рекомендований. Робиться в панелі DigitalOcean, дані не втрачаються.

**Б. Лишити дроплет, але:**
1. додати 2 ГБ swap:
   ```bash
   fallocate -l 2G /swapfile && chmod 600 /swapfile
   mkswap /swapfile && swapon /swapfile
   echo '/swapfile none swap sw 0 0' >> /etc/fstab
   ```
2. лишити жорсткий ліміт `mem_limit: 512m` у compose (він уже стоїть).

Ліміт означає: у найгіршому випадку **падає n8n, а ЕРП живе**. Це і є сенс ліміту.

⚠️ Без А або Б ставити не можна. `install.sh` сам відмовиться, якщо вільно
менше 400 МБ.

## 3. Що потрібно від власниці

Без цього перехід не зробити — це не технічні дрібниці, а рішення й доступи:

| # | Що | Чому саме ви |
|---|---|---|
| 1 | **Рішення А чи Б** (збільшити сервер / лишити зі swap) | це гроші |
| 2 | **Піддомен**, напр. `n8n.unitex.od.ua`, і A-запис у DNS на IP сервера | доступ до реєстратора домену тільки у вас |
| 3 | **Пошта й пароль власника n8n** — задаєте при першому вході | пароль не повинен проходити через мене |
| 4 | **Доступи до сервісів заново** (див. нижче) | вони ваші, і в хмарі їх не «скопіювати» |
| 5 | **Рішення, коли вимикати n8n Cloud** | тільки після тижня паралельної роботи |
| 6 | **Оновити посилання на вебхуки** там, де ви їх комусь давали | адреси зміняться |

### Про доступи (пункт 4) — найважливіше

**n8n Cloud не віддає паролі назовні.** Вивантажені воркфлоу містять схему, а
доступи — ні (я їх ще й свідомо вирізала при копії). Тому в новому n8n їх треба
завести **вручну**, по одному:

- **Telegram Bot Token** — бот «Максим» (BotFather);
- **Google (OAuth)** — Sheets, для воркфлоу, що ще ходять у таблиці;
- **Maersk** — `client_id` / `client_secret`.
  ⚠️ Вони колись лежали у воркфлоу відкритим текстом і гуляли в zip через чат —
  **при перенесенні їх варто перевипустити**, а не переносити старі;
- **Claude API** — для «Дайджест новин ліній» і «Контроль прибуття»;
- **Пошта (SMTP/IMAP)** — для листів і алертів.

## 4. Порядок переходу

Кожен крок перевіряється до наступного. Хмара працює весь цей час.

1. **Ресурси** — А або Б (розділ 2).
2. **Перевірка готовності** — нічого не змінює:
   ```bash
   bash /root/Iryna_Karmazina/server/n8n/install.sh --check
   ```
3. **Установка**:
   ```bash
   bash /root/Iryna_Karmazina/server/n8n/install.sh n8n.unitex.od.ua
   ```
   Створює `/root/n8n-data`, генерує **ключ шифрування**, піднімає контейнер
   на `127.0.0.1:5678`. Назовні поки не видно.
4. **🔑 Ключ шифрування — у менеджер паролів.** Показати:
   ```bash
   grep N8N_ENCRYPTION_KEY /root/n8n-data/.env
   ```
   Без нього резервна копія n8n марна: доступи не розшифрувати.
5. **DNS** — A-запис піддомену на IP сервера.
6. **Caddy** — дописати блок у `/root/Caddyfile` (скрипт сам НЕ чіпає бойовий файл):
   ```
   n8n.unitex.od.ua {
       reverse_proxy 127.0.0.1:5678
   }
   ```
   ```bash
   docker exec caddy caddy validate --config /etc/caddy/Caddyfile
   docker exec caddy caddy reload  --config /etc/caddy/Caddyfile
   ```
7. **Перший вхід** — завести власника (пошта + пароль).
8. **Резервні копії** — додати `/root/n8n-data/.n8n` до `PATHS` у `server/backup.py`,
   інакше воркфлоу не потраплять у щоденну копію. Перевірити наступного дня
   за `/root/backup_log.tsv`.
9. **Перенесення воркфлоу — ПО ОДНОМУ**, через Import from File; файли лежать
   у `n8n_backup/` цього репозиторію. Спершу **вимкненими**, завести доступи,
   прогнати вручну, і тільки тоді вмикати. Починати з найпростішого
   (`finrep-sheets-proxy`), бота «Максим» — останнім.
10. **Тиждень паралельної роботи.** Активний лишається ОДИН примірник кожного
    воркфлоу — інакше дві копії робитимуть те саме двічі.
11. **Вимкнення хмари** — тільки після тижня без збоїв і тільки за вашим словом.

⚠️ У n8n Cloud **нічого не видаляти**. Вимкнути ≠ видалити (правило 6).

## 5. Обслуговування — чесно

**Оновлення** — одна команда, з копією і автоматичним відкатом:

```bash
bash /root/Iryna_Karmazina/server/n8n/update.sh          # на останню версію
bash /root/Iryna_Karmazina/server/n8n/update.sh 1.62.4   # на конкретну
bash /root/Iryna_Karmazina/server/n8n/update.sh --rollback
```

Скрипт зупиняє n8n, робить копію теки даних, піднімає нову версію і 60 секунд
чекає `healthz`. Не піднялось — сам повертає стару версію і стару копію.
Невдалий стан не видаляється, а зберігається поруч.

**Що я можу:** ставити, оновлювати, відкочувати, чинити, переносити воркфлоу,
писати нові — усе це через Git Relay, не заходячи руками на сервер.

**Чого я не можу:**

- **чергувати.** Впаде о 3-й ночі — лежатиме до ранку. Тому оновлювати треба
  вдень і за вашим словом, а не автоматично;
- **гарантувати сумісність.** n8n оновлюється часто, буває ламає воркфлоу.
  Саме тому оновлення тут із відкатом, а не `pull latest`;
- **бачити, що воркфлоу відпрацював неправильно**, якщо ніхто не дивиться.
  Потрібне сповіщення про помилки — окрема невелика робота, зробити варто одразу.

**Рекомендація щодо ритму:** оновлювати не частіше разу на місяць і тільки
коли є причина (виправлення безпеки або потрібна нова можливість). Працює —
не чіпати.
