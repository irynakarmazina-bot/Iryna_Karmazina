# Кабінет клієнта — як влаштований і як викласти

`cabinet.unitex.od.ua` → Caddy (443) → `127.0.0.1:8793` → `server/cabinet.py` → NocoDB.

Кабінет **не має файлу на диску**. Сторінка збирається на кожен запит уже після
того, як сервер упізнав, хто прийшов, і бере лише угоди його компанії. Це і є
головна відмінність від прототипу `client_cabinet/build_preview.py`, який
записував статичний `cabinet.html` — його бачив будь-хто, хто знав адресу.

## З чого складається

| Файл | Що це |
|---|---|
| `server/cabinet.py` | сам кабінет: вхід, сесії, фільтрація, документи, журнал |
| `server/cabinet_admin.py` | акаунти клієнтів (завести, заблокувати, новий пароль) |
| `server/unitex-cabinet.service` | служба systemd |
| `client_cabinet/build_preview.py` | **спільний** шаблон сторінки + список дозволених колонок |
| `scripts/check_cabinet.sh` | шлюз перед викладенням (86 перевірок) |

Вигляд сторінки лежить в ОДНОМУ місці — `TPL` у `build_preview.py`. Кабінет його
імпортує, а не копіює: інакше дві копії розійдуться, і це вже коштувало нам
одного втраченого дня роботи (02.08.2026).

## Що де зберігається

- `/root/cabinet/cabinet.db` — акаунти клієнтів, сесії, журнал. **Окремо від
  NocoDB** свідомо: у NocoDB `v.pontus@unitex.od.ua` має роль `editor`, тобто
  бачить усі таблиці, а хеші паролів клієнтів його не стосуються.
- `/root/cabinet/secret` — ключ для міток форм (0600).
- `/root/cabinet.log` — журнал служби.

⚠️ **Додати `/root/cabinet/` у `server/backup.py`** — зараз його там немає,
тобто акаунти клієнтів у нічний бекап НЕ потрапляють. Це відкрите питання.

## Викладення (перший раз)

```bash
# 1. служба
cp /root/Iryna_Karmazina/server/unitex-cabinet.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now unitex-cabinet
systemctl status unitex-cabinet --no-pager

# 2. перевірка, що піднялась (має бути ok)
curl -s http://127.0.0.1:8793/health

# 3. Caddy — ДОДАТИ блок, нічого наявного не чіпаючи
#    (сертифікат Caddy візьме сам: A-запис cabinet.unitex.od.ua → 134.209.94.12 вже є)
cat >> /etc/caddy/Caddyfile <<'EOF'

cabinet.unitex.od.ua {
    encode gzip
    reverse_proxy 127.0.0.1:8793
}
EOF
caddy validate --config /etc/caddy/Caddyfile   # спершу перевірити!
systemctl reload caddy

# 4. перевірка ззовні
curl -sI https://cabinet.unitex.od.ua/ | head -3
```

## Акаунти клієнтів

```bash
cd /root/Iryna_Karmazina/server
python3 cabinet_admin.py clients                      # точні назви компаній
python3 cabinet_admin.py add --email ivan@mirandor.ua \
        --client "Мірандор" --name "Іван"             # пароль покаже ОДИН раз
python3 cabinet_admin.py list
python3 cabinet_admin.py passwd --email ivan@mirandor.ua   # новий тимчасовий
python3 cabinet_admin.py block  --email ivan@mirandor.ua   # закрити доступ
python3 cabinet_admin.py log --limit 40                    # хто що робив
```

Пароль видно рівно один раз, у терміналі. У базі — лише scrypt-хеш. У журнал,
у репозиторій і в переписку пароль не потрапляє. При першому вході кабінет не
пустить далі, доки клієнт не придумає свій.

Одна компанія = скільки завгодно людей: заводьте кілька акаунтів з тією самою
`--client`.

**Видалення акаунтів у скрипті немає свідомо** — доступ закривається `block`,
рядок і журнал лишаються (правило 6 у CLAUDE.md).

## Що саме бачить клієнт

- Тільки угоди своєї компанії — збіг назви **точний**, скасовані відкинуті.
- Тільки колонки зі списку `CLIENT_COLS` (`build_preview.py`). Менеджера,
  профіту, ставок і внутрішнього коментаря там немає — вони не виходять із
  сервера взагалі, а не «ховаються» в браузері.
- З коментарів — лише `Коментар клієнту`.
- З документів — лише типи з `CLIENT_DOCS` (префікс `[Тип]` у назві файла).
  Файл віддає сервер після перевірки, чия це угода; шлях у сховищі в браузер
  не потрапляє.
- Фінансів немає взагалі (рішення користувачки).

## Перед будь-яким викладенням

```bash
bash scripts/check_cabinet.sh      # має закінчитись CABINET_OK
```

Прогнати обов'язково і після правки `client_cabinet/build_preview.py` — сторінка
у прототипу і в кабінету спільна. Живої бази перевірка не торкається.

## Чого ще НЕМАЄ (не вигадувати, що є)

- Клієнт **не може писати** в кабінеті. Форму «Питання по вантажу» з прототипу
  прибрано: показувати кнопку, яка нічого не робить, не можна.
- Клієнт **не може прикріплювати** файли.
- Акаунти заводяться тільки з термінала — екрана в ЕРП поки немає.
- Сповіщень (про новий документ, зміну статусу) немає.
- `/root/cabinet/` не в бекапах (див. вище).
