### 1. Що це за система

| Частина | Адреса | Хто нею користується |

### 2. Де воно фізично

**Сервер:** VPS DigitalOcean, Ubuntu, `/root/Iryna_Karmazina` — клон цього репозиторію.
Точна адреса й ключі доступу — у `server/RESTORE.md`.

Схема запитів:

```
Інтернет
  └── Caddy (443, у docker)
        ├── /            → /root/unitex-os-www/index.html   ← ЕРП, статичний файл
        ├── /api/*       → 127.0.0.1:8792  gateway.py       ← прошарок прав
        │                     └──────────→ 127.0.0.1:8080   NocoDB (docker)
        ├── /download/*  → 127.0.0.1:8080  NocoDB           ← вкладення, повз прошарок
        └── cabinet.unitex.od.ua → 127.0.0.1:8793 cabinet.py ← кабінет клієнта
```

Окремо, поза сервером: **n8n Cloud** (`irynakarmazina.app.n8n.cloud`) — трекінг
Maersk щодня о 07:00 і бот «Максим». Воркфлоу зберігаються в хмарі n8n,
а не в цьому репозиторії.

#### Служби systemd

| Служба | Що робить | Файл у репо |
|---|---|---|
| `mybot` | особистий Telegram-бот | `bot.py`, `agent_bot.py` |
| `cmdrunner` | Git Relay — виконує команди з `cmds/pending.json` | `cmd_runner.py` |
| `unitex-gateway` | прошарок прав перед NocoDB (порт 8792) | `server/gateway.py` |
| `unitex-cabinet` | кабінет клієнта (порт 8793) | `server/cabinet.py` |
| `unitex-backup.timer` | резервна копія щодня о 03:30 | `server/backup.py` |
| `cashtrigger` | вивантаження рухів кас з 1С | `finrep/cash_trigger.py` |

⚠️ **Важливо:** служба `unitex-gateway` запускає `/root/gateway.py`, а **не** файл
із репозиторію. Правки в `server/gateway.py` самі на сервер не доїжджають —
треба копіювати вручну.

### 4. Як щось змінити

#### Фасад ЕРП (`www/index.html`)

**Тільки скриптом і тільки з `main`:**


Ручне `cp` заборонене. Скрипт робить бекап, ганяє перевірки, пише журнал і
**відмовляється** класти файл поверх версії, якої немає в історії гілки.
Причина заборони описана в шапці самого скрипта (02.08.2026 ручний деплой
затер денну роботу паралельної сесії).

Перед викладенням обов'язково:

```bash
bash scripts/check_facade.sh www/index.html
```

`CHECK_FAIL` — не викладати.

#### Решта коду

Коміт у `main` → автодеплой на сервері підхопить протягом хвилини
(`/root/autodeploy.sh` робить `git pull` і перезапускає служби).

неможливо розшифрувати**. Це єдине місце в системі, де помилка необоротна.

### 6. Що треба знати про обмеження

- **NocoDB — план Free, самохостинг.** Немає власних ролей, прав на таблиці й
  поля, журналу змін, версій записів. Бізнес-правила живуть у прошарку
  (`server/gateway.py`), а не в базі.
- **Прошарок зараз у режимі спостереження** — рахує й пише відмови в
  `/root/gateway.log`, але нікого не блокує.
- **1С «Експедитор» — тільки читання.** Усі 280 угод у базі проведені;
  запис у проведений документ через OData не перевірявся.
- **Ліцензія NocoDB** — Sustainable Use License (з версії 0.301.0, не open source).
  Внутрішнє використання дозволене; надавати сам NocoDB третім особам — ні.

### 8. Головний ризик системи

Технічно платформа працює сама: сервер, служби, бекапи, трекінг не потребують

# 3. Аварійна картка — коли щось не працює

_Джерело: `server/EMERGENCY.md`_

Одна сторінка. Розрахована на те, що читатиме не програміст, у поганий момент.
Дані відновлювати — `server/RESTORE.md`. Загальний опис системи — `README.md`.

**Правило номер нуль: спершу подивитись, потім міняти. Нічого не видаляти.**

Зайти на сервер:

```bash
ssh -i ~/.ssh/unitex_droplet root@134.209.94.12
```

Якщо ключ не працює: панель DigitalOcean → дроплет → **Access** →
**Reset Root Password** → **Launch Droplet Console**.

---

### Перше, що зробити завжди — загальний огляд

```bash
systemctl --failed
docker ps
df -h /
tail -20 /root/backup_log.tsv
```

- `systemctl --failed` — які служби впали
- `docker ps` — мають бути **caddy** і **nocodb**
- `df -h /` — якщо диск заповнений на 100%, падати буде все підряд
- останній рядок журналу копій має бути за сьогодні або вчора

---

### Симптом → що робити

#### ЕРП не відкривається взагалі (сайт не відповідає)

```bash
docker ps | grep caddy || docker start caddy
docker logs --tail 50 caddy
curl -s -o /dev/null -w "%{http_code}\n" https://cabinet.unitex.od.ua/
```

#### Сайт відкрився, але порожній / «не вдалося завантажити дані»

Значить, фасад живий, а дані не приходять. Перевірити ланцюг знизу вгору:

```bash
curl -s http://127.0.0.1:8080/api/v1/version        # NocoDB — має відповісти
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8792/   # прошарок
systemctl status unitex-gateway --no-pager | head -15
tail -30 /root/gateway.log
```

- NocoDB мовчить → `docker start nocodb`, далі `docker logs --tail 50 nocodb`
- прошарок мовчить → `systemctl restart unitex-gateway`
- у `gateway.log` рядки про відмови під час звичайної роботи → прошарок
  блокує зайве. **Тимчасовий обхід:** повернути маршрут повз нього
  (див. «Відкат прошарку» нижче).

#### Сторінка ЕРП зламалась після викладення

```bash
bash /root/Iryna_Karmazina/server/rollback_ui.sh        # показати версії
bash /root/Iryna_Karmazina/server/rollback_ui.sh 1      # відкотити на крок назад
```

Нічого не видаляється: поточна версія теж лягає в бекапи.

#### Кабінет клієнта не працює

```bash
systemctl status unitex-cabinet --no-pager | head -15
systemctl restart unitex-cabinet
tail -30 /root/cabinet.log
```

#### Telegram-бот мовчить

```bash
systemctl status mybot --no-pager | head -15
journalctl -u mybot -n 50 --no-pager
systemctl restart mybot
```

#### Не працює трекінг Maersk або бот «Максим»

Це **не на сервері**. Вони живуть у n8n Cloud —
`irynakarmazina.app.n8n.cloud`, розділ Executions: там видно, чи запускалось
і на чому впало.

#### Резервні копії перестали робитись

```bash
systemctl list-timers unitex-backup.timer
journalctl -u unitex-backup -n 50 --no-pager
systemctl start unitex-backup.service     # зробити копію просто зараз
tail -5 /root/backup_log.tsv
```

Перевірити: сайт має відкритись і показати дані.
Це безпечно: так система працювала до 13.08.2026.

- ❌ не міняти базу `noco.db` на місці без зупинки контейнера й копії поруч

2. Відновлення бази — `server/RESTORE.md`, крок за кроком.
3. Якщо сервера більше немає взагалі — `server/RESTORE.md`, останній розділ

**Пароль від копій** — менеджер «Паролі», запис «Юнітекс резервні копії».

### 2. Не працює SSH до сервера

Це **не тупик**. Порядок дій:

1. **Перевірити ключ на своєму комп'ютері:**
   ```bash
   ls -la ~/.ssh/unitex_droplet
   ssh -i ~/.ssh/unitex_droplet root@134.209.94.12
   ```
2. **Якщо ключа немає або Mac недоступний** — заходити через панель провайдера:
   DigitalOcean → потрібний дроплет → **Access** → **Reset Root Password**
   (новий пароль прийде на пошту) → **Launch Droplet Console**.
   Консоль працює в браузері й ключа не потребує.
3. **Опинившись у консолі**, покласти новий ключ:
   ```bash
   nano ~/.ssh/authorized_keys      # додати публічну частину нового ключа
   systemctl reload ssh
   ```

⚠️ Вхід у SSH **по паролю вимкнено** (`/etc/ssh/sshd_config.d/00-hardening.conf`).
Тому «знаю пароль root» без консолі провайдера не допоможе — тільки ключ або консоль.

### 3. Немає доступу до GitHub або DigitalOcean

Це верхній рівень: **хто володіє акаунтом, той володіє системою.**

- **DigitalOcean** — тут живе сам сервер. Втрата акаунта = втрата сервера.
  Відновлення: пошта акаунта → «Забули пароль» → резервні коди двофакторної.
- **GitHub** (`irynakarmazina-bot/Iryna_Karmazina`) — тут увесь код і документація.
  Втрата акаунта не зупиняє сервер: він працює далі, але **оновити його не вийде**.
  Локальна копія репозиторію є на сервері в `/root/Iryna_Karmazina` — код звідти
  не зникає.

📌 **Заповнити один раз і тримати актуальним** (я цих даних не знаю і вигадувати
не буду):

| Що | Хто власник | Пошта відновлення | Резервні коди 2FA — де |
|---|---|---|---|
| DigitalOcean | | | |
| GitHub | | | |
| n8n Cloud | | | |
| Google Drive (бекапи) | | | |
| Реєстратор домену `unitex.od.ua` | | | |

⚠️ **Домен окремо.** `cabinet.unitex.od.ua` працює, поки в DNS стоїть запис на
адресу сервера. Втрата доступу до реєстратора або несплата домену вимикає кабінет
клієнтів, навіть якщо сервер цілком справний. Хто платить за домен і коли він
спливає — записати в таблицю вище.

### 4. n8n Cloud і Google Drive

- **n8n Cloud** (`irynakarmazina.app.n8n.cloud`) — там трекінг Maersk і бот
  «Максим». Втрата акаунта зупиняє їх, але **не чіпає ЕРП**: платформа і кабінет
  працюють далі, просто перестане оновлюватись рух контейнерів.
  Копія схем воркфлоу — `n8n_backup/` у репозиторії (`scripts/n8n_backup.py`).
  Доступи (credentials) у копію навмисно не входять — їх заводити заново.
- **Google Drive** — туди щодня вивантажуються резервні копії. Втрата доступу
  не ламає нічого одразу, але лишає копії тільки на самому сервері, тобто зникає
  захист від «сервера більше немає».

### 5. Клієнт не може зайти в кабінет

Акаунти кабінету лежать **окремо** від ЕРП (`/root/cabinet/cabinet.db`).
З інтернету завести собі доступ не може ніхто — тільки з сервера:

```bash
cd /root/Iryna_Karmazina/server
python3 cabinet_admin.py list                          # хто заведений
python3 cabinet_admin.py passwd --email ivan@firma.ua  # новий пароль
python3 cabinet_admin.py block  --email ivan@firma.ua  # закрити доступ
python3 cabinet_admin.py log --limit 30                # журнал входів
```

Пароль показується **рівно один раз**, у терміналі. У базі — тільки хеш.
Передавати клієнту не через відкритий чат.

⚠️ Видалення акаунтів у скрипті немає свідомо: доступ закривається `block`,
запис і журнал лишаються.

### 6. Відновлення ЗМІСТУ ЕРП (дані зникли або зіпсовані)

Коротко; покроково — `server/RESTORE.md`.

1. **Нічого не виправляти «на живому».** Спершу зробити копію поточного стану:
   ```bash
   systemctl start unitex-backup.service
   tail -3 /root/backup_log.tsv
   ```
2. **Знайти копію за день до поломки:** `ls -1t /root/backups/`
3. **Розшифрувати й перевірити цілість** (`PRAGMA integrity_check` має дати `ok`)
4. **Замінити базу** із зупинкою контейнера і копією поруч
5. **Подивитись очима**: диспетчеризація, клієнти, статуси

Якщо сервера немає взагалі — останній розділ `RESTORE.md`: копії лежать також
на Google Drive.

🔴 **Єдина необоротна поломка в усій системі — втрата пароля від резервних копій.**
Він у менеджері «Паролі» (запис «Юнітекс резервні копії») і в `/root/.backup-pass`.
Друга копія марна саме тоді, коли потрібна найбільше (сервера немає).
**Дія на сьогодні: покласти пароль у друге місце поза сервером і поза Mac.**

### 7. Порядок дій, якщо незрозуміло взагалі нічого

1. Не міняти нічого перші п'ять хвилин. Записати, що саме не працює і з якого часу.
2. `server/EMERGENCY.md` → блок «Перше, що зробити завжди».
3. Якщо зрозуміло, що це доступ — цей файл, потрібний розділ.
4. Якщо зрозуміло, що зникли дані — `server/RESTORE.md`.
5. Якщо після всього не зрозуміло — **зробити резервну копію і зупинитись**.
   Зіпсований стан, з якого є копія, відновлюється. Зіпсований стан після
   поспішних дій — не завжди.

### Відновлення бази

#### Крок 1. Зайти на сервер


Якщо ключ не працює або Mac недоступний — панель DigitalOcean → дроплет →

```bash
ls -1t /root/backups/
```

Найсвіжіша — зверху. Якщо треба стан «до поломки», бери копію за день **до** того,

Спитає пароль — узяти з менеджера «Паролі», запис «Юнітекс резервні копії».

```bash
tar -xzf /root/restore/archive.tar.gz -C /root/restore
ls -la /root/restore
```

#### Крок 4. Переконатися, що копія ціла — ДО того, як щось замінювати

```bash
python3 -c "import sqlite3; print(sqlite3.connect('/root/restore/noco.db').execute('PRAGMA integrity_check').fetchone()[0])"
```
Має вивести `ok`. Якщо ні — **не продовжувати**, узяти попередню копію.

Скільки в ній записів:

### Якщо сервера більше немає взагалі

1. Створити новий дроплет Ubuntu 24.04 у DigitalOcean.
2. Поставити docker, підняти NocoDB із тим самим монтуванням:
   `-v /root/nocodb-data:/usr/app/data -p 127.0.0.1:8080:8080`
   (точні параметри старого контейнера збережені у файлах
   `/root/nocodb-container-*.json` і в самих копіях).
3. Покласти `noco.db` з копії в `/root/nocodb-data/`.
4. Повернути `Caddyfile` і решту з `config/`.
5. Клонувати репозиторій у `/root/Iryna_Karmazina` і викласти фасад:
   `bash server/deploy_ui.sh main`.
6. Перевірити фаєрвол: вхідні тільки 22, 80, 443.

⚠️ Для цього кроку копії мають лежати **не на тому сервері, якого вже немає**.
Саме тому потрібне вивантаження назовні (DigitalOcean Spaces / Google Drive).
