# Юнітекс OS — карта системи

Це репозиторій платформи транспортно-експедиторської компанії «Юнітекс»:
ЕРП, кабінет клієнта, фінансова звітність, інтеграції з 1С і морськими лініями,
Telegram-боти.

**Якщо ви тут уперше — прочитайте цей файл цілком. Він відповідає на питання
«що це, де воно живе і з чого починати».**

Якщо щось зламалось просто зараз — `server/EMERGENCY.md`.
Якщо треба відновити дані — `server/RESTORE.md`.

---

## 1. Що це за система

| Частина | Адреса | Хто нею користується |
|---|---|---|
| **ЕРП (фасад)** | сайт на сервері | співробітники Юнітекса |
| **Кабінет клієнта** | cabinet.unitex.od.ua | клієнти компанії |
| **Telegram-бот «Максим»** | Telegram | клієнти компанії |
| **Telegram-бот особистий** | Telegram | власниця |

Дані живуть в одному місці — **NocoDB** (SQLite-файл на сервері).
Первинний бухгалтерський облік — у **1С «Експедитор»** (окрема система, до неї
ходимо через OData, тільки на читання).

---

## 2. Де воно фізично

**Сервер:** VPS DigitalOcean, Ubuntu, `/root/Iryna_Karmazina` — клон цього репозиторію.
Точна адреса й ключі доступу — у `server/RESTORE.md`.

Схема запитів:

```
Інтернет
  └── Caddy (443, у docker)
        ├── /            → /root/unitex-os-www/index.html   ← ЕРП, статичний файл
        ├── /api/*       → 127.0.0.1:8792  gateway.py       ← прошарок прав
        │                     └──────────→ 127.0.0.1:8080   NocoDB (docker)
        ├── /download/*  → 127.0.0.1:8080  NocoDB           ← вкладення, повз прошарок
        └── cabinet.unitex.od.ua → 127.0.0.1:8793 cabinet.py ← кабінет клієнта
```

Окремо, поза сервером: **n8n Cloud** (`irynakarmazina.app.n8n.cloud`) — трекінг
Maersk щодня о 07:00 і бот «Максим». Воркфлоу зберігаються в хмарі n8n,
а не в цьому репозиторії.

### Служби systemd

| Служба | Що робить | Файл у репо |
|---|---|---|
| `mybot` | особистий Telegram-бот | `bot.py`, `agent_bot.py` |
| `cmdrunner` | Git Relay — виконує команди з `cmds/pending.json` | `cmd_runner.py` |
| `unitex-gateway` | прошарок прав перед NocoDB (порт 8792) | `server/gateway.py` |
| `unitex-cabinet` | кабінет клієнта (порт 8793) | `server/cabinet.py` |
| `unitex-backup.timer` | резервна копія щодня о 03:30 | `server/backup.py` |
| `cashtrigger` | вивантаження рухів кас з 1С | `finrep/cash_trigger.py` |

⚠️ **Важливо:** служба `unitex-gateway` запускає `/root/gateway.py`, а **не** файл
із репозиторію. Правки в `server/gateway.py` самі на сервер не доїжджають —
треба копіювати вручну.

## 3. Структура репозиторію

| Тека | Що всередині |
|---|---|
| `www/` | **фасад ЕРП** — `index.html` (усі 10 сторінок в одному файлі), фінансовий дашборд |
| `server/` | усе, що працює на сервері: прошарок, кабінет, бекапи, деплой, документація |
| `scripts/` | перевірки перед викладенням (шлюзи якості) |
| `finrep/` | фінансова звітність, обмін з 1С через OData |
| `ekspedytor/` | автоматизація 1С «Експедитор» (Computer Use, `/invoice`) |
| `client_cabinet/` | шаблон сторінки кабінету (спільний з `server/cabinet.py`) |
| `handoff/` | розбори й передача контексту між сесіями |
| `cmds/` | Git Relay: `pending.json` — команда, `result.json` — результат |
| `audit/`, `n8n_dz/`, `direct_sync/`, `doc-templates/` | допоміжні матеріали |

Головні документи:

- `CLAUDE.md` — правила роботи. **Читати першим.**
- `MEMORY.md` — журнал сесій і постійні факти. `MEMORY_ARCHIVE.md` — старе.
- `server/RESTORE.md` — відновлення з резервної копії.
- `server/CABINET.md` — як влаштований кабінет клієнта.
- `server/EMERGENCY.md` — що робити, коли лежить.
- `handoff/` — рішення й розбори за датами.

## 4. Як щось змінити

### Фасад ЕРП (`www/index.html`)

**Тільки скриптом і тільки з `main`:**

```bash
bash /root/Iryna_Karmazina/server/deploy_ui.sh main     # викласти
bash /root/Iryna_Karmazina/server/deploy_ui.sh --check  # тільки перевірити
bash /root/Iryna_Karmazina/server/rollback_ui.sh        # відкат
```

Ручне `cp` заборонене. Скрипт робить бекап, ганяє перевірки, пише журнал і
**відмовляється** класти файл поверх версії, якої немає в історії гілки.
Причина заборони описана в шапці самого скрипта (02.08.2026 ручний деплой
затер денну роботу паралельної сесії).

Перед викладенням обов'язково:

```bash
bash scripts/check_facade.sh www/index.html
```

`CHECK_FAIL` — не викладати.

### Решта коду

Коміт у `main` → автодеплой на сервері підхопить протягом хвилини
(`/root/autodeploy.sh` робить `git pull` і перезапускає служби).

## 5. Резервні копії

- Щодня о 03:30 за Києвом, `server/backup.py`
- Усередині: база NocoDB, вкладення, конфігурація, якої немає в git
- Шифрування gpg, вивантаження на Google Drive через rclone
- Зберігаються 10 днів
- Журнал: `/root/backup_log.tsv`

Перевірити, що копії робляться:

```bash
tail -5 /root/backup_log.tsv
systemctl list-timers unitex-backup.timer
```

Відновлення — покроково в `server/RESTORE.md`. Наскрізне відновлення з Google Drive
перевірено 08.08.2026: кількість записів збіглася.

⚠️ **Пароль для розшифрування** лежить у менеджері «Паролі» власниці і в
`/root/.backup-pass` на сервері. Якщо зникне і те, і те — **вивантажені копії
неможливо розшифрувати**. Це єдине місце в системі, де помилка необоротна.

## 6. Що треба знати про обмеження

- **NocoDB — план Free, самохостинг.** Немає власних ролей, прав на таблиці й
  поля, журналу змін, версій записів. Бізнес-правила живуть у прошарку
  (`server/gateway.py`), а не в базі.
- **Прошарок зараз у режимі спостереження** — рахує й пише відмови в
  `/root/gateway.log`, але нікого не блокує.
- **1С «Експедитор» — тільки читання.** Усі 280 угод у базі проведені;
  запис у проведений документ через OData не перевірявся.
- **Ліцензія NocoDB** — Sustainable Use License (з версії 0.301.0, не open source).
  Внутрішнє використання дозволене; надавати сам NocoDB третім особам — ні.

## 7. Секрети — де вони і чого тут немає

**У репозиторії паролів немає і бути не повинно.**

| Що | Де лежить |
|---|---|
| Ключі й паролі сервера | `.env` на VPS |
| Пароль резервних копій | «Паролі» на Mac + `/root/.backup-pass` |
| Ключ n8n API | `~/.n8n_env` на сервері |
| Доступи n8n, ліній, Maersk | credentials усередині n8n |
| Ключ SSH до сервера | Mac власниці, `~/.ssh/unitex_droplet` |

## 8. Головний ризик системи

Технічно платформа працює сама: сервер, служби, бекапи, трекінг не потребують
нічиєї присутності. Але **розвиває й лагодить її одна людина**, і знання про те,
як усе влаштовано, живе в цьому репозиторії та в `MEMORY.md`, а не в команді.

Тому будь-яку зміну треба **записувати сюди одразу**, а не «потім».
Це не бюрократія — це єдине, що робить систему передаваною.
